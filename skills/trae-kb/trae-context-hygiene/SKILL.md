# 上下文治理

## 三个不同的问题，别用一种办法

| 问题 | 症状 | 正确手段 |
| --- | --- | --- |
| 该给的资料没给 | 模型凭空猜、答非所问 | **精准引用**（文件/段落/历史结论） |
| 给的资料太多太杂 | 关键点被淹没、成本高 | **压缩与裁剪** |
| 每轮重复塞同样的东西 | 前缀不稳定、缓存失效、成本翻倍 | **静态前置 + 动态后置** |

## 精准引用（比压缩更划算）

引用原则：**只给完成任务必需的最小片段**，并标明来源。

- 引用文件：给路径 + 相关片段，不给整仓。
- 引用历史：给「结论 + 关键证据」，不给全部对话。
- 引用规范：给条目编号 + 与本任务相关的 3-5 条。

引用格式建议：

```text
【引用】src/gateway/chat.rs:468-520（chat.send 入口，含参数解析与 API Key 门禁）
```

反例：把 5000 行文件整段贴进上下文 —— 既贵又稀释注意力。

## 压缩（何时做、怎么做）

**何时压缩**：上下文占用超过阈值、或任务阶段切换（调研 → 实施）后旧材料已无用。

**压缩保留什么**：

1. 目标与验收标准
2. 已确认的事实与决策（含理由）
3. 未决问题与阻塞
4. 关键文件路径与改动点
5. 已失败的尝试（避免重复踩坑）

**压缩丢掉什么**：原始日志、完整文件内容、被否决方案的细节、重复的检索结果。

**压缩输出模板**：

```markdown
## 目标
## 已确认事实（含来源）
## 已完成 / 未完成
## 关键文件与位置
## 未决问题
## 失败尝试（不要再试）
```

## 前缀稳定（省钱且更稳）

模型侧的前缀缓存只在**前缀完全一致**时命中。因此：

1. **静态段前置**：角色、规则、工作区说明、工具清单 —— 每轮完全相同。
2. **动态段后置**：记忆召回、检索片段、本轮引用材料。
3. **禁止抖动**：不要在静态段里写时间戳、随机 id、实时计数。
4. **规则变更代价**：改规则会让整段前缀失效，一次性改完，不要每轮微调。

## 长任务的上下文节奏

1. **开工**：目标 + 验收 + 已知约束（短）。
2. **进行中**：只保留当前步骤所需材料；完成的步骤压成一行结论。
3. **阶段切换**：主动压缩一次，丢掉上一阶段的过程细节。
4. **收尾**：用验收标准逐条核对，而不是回看全部过程。

## 常见误区

| 误区 | 后果 | 纠正 |
| --- | --- | --- |
| 把整个仓库塞进上下文 | 贵、慢、注意力分散 | 按需引用片段 |
| 压缩时连结论一起删 | 重复劳动、前后矛盾 | 保留事实与决策，删过程 |
| 静态段里放实时数据 | 缓存永不命中 | 动态内容全部后置 |
| 反复小改规则 | 前缀反复失效 | 批量改、一次生效 |
| 长任务不设里程碑 | 中途跑偏无人发现 | 每阶段验收一次 |

## 自检清单

- [ ] 本轮引用的材料都是「完成任务必需」的最小集
- [ ] 每个引用都标了来源（路径/行号/来源文档）
- [ ] 静态段无时间戳与随机值
- [ ] 阶段切换后已压缩旧过程
- [ ] 压缩结果包含目标、事实、未决、失败尝试
