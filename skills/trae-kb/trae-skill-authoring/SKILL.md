# 写一个真正好用的 Skill

## 何时用本技能

- 用户要把某类**重复任务**沉淀成可复用能力（而不是一次性 prompt）。
- 用户抱怨「Agent 每次都做得不一样」「规则写了没用」「技能写了不生效」。
- 需要把一份长规范压缩成 Agent 能稳定执行的流程。

不要用本技能做：单次问答、一次性脚本、只改一个文件的普通编码任务。

## 心智模型：Skill = 菜谱，不是按钮

| 概念 | 类比 | 谁触发 | 解决什么 |
| --- | --- | --- | --- |
| 斜杠命令 / 快捷指令 | 微波炉上的「爆米花」按钮 | **用户**手动 | 复用一段固定 prompt |
| MCP 原子工具 | 一把刀、一个烤箱 | 模型调用 | 连接外部系统、拿数据 |
| **Skill 技能** | 一本完整菜谱 | **模型按意图自动匹配** | 把「用哪些工具、按什么步骤、注意什么」流程化 |

判断口诀：**能被一次工具调用完成 → 做工具；需要多步判断与取舍 → 做技能；只是固定一句话 → 做命令/规则。**

## 三层渐进加载（决定你怎么写）

1. **元数据层（常驻）**：`name` + `description`，约 100 token/个。它决定「模型会不会选中你」。必须写清**使用场景 + 触发条件 + 产出物**。
2. **说明文档层（触发时加载）**：`SKILL.md` 正文，建议 **< 5000 token**。写流程、步骤、判断规则、反例。
3. **资源层（按需读取）**：脚本、模板、长参考文档。**正文里只写「何时读哪个文件」，不要把长内容抄进正文。**

推论：正文越长 ≠ 越好。把大段资料放进 `references/`，正文只留索引与判断逻辑。

## 五项质量闸门（写完逐条自检）

### 1. 原子性（单一职责）

一个 Skill 只回答一类问题。反例：「既做数据查询、又做图表、又发邮件」——应拆成三个原子技能，再用一个 SOP 技能把它们串起来。

自检：如果描述里出现两个以上「并且」，就拆。

### 2. 给例子（最关键）

比起解释，模型更吃示例。至少给 **1 组好例子 + 1 组坏例子**，标明差异点。

```text
好：输入「帮我查上海 10 月 1-7 日天气」→ 调用 weather(city=上海, from=2026-10-01, to=2026-10-07)
坏：输入同上 → 直接编造「晴，25 度」
差异：坏例子缺少工具调用与数据来源。
```

### 3. 立规矩（结构化指令）

- **定角色**：一句话说明「你是哪类专家、对什么负责」。
- **拆步骤**：编号步骤，每步写「输入 → 动作 → 输出」。
- **画红线**：明确写出禁止事项（编造数据、跳过验证、越权改文件、声称执行过未执行的操作）。

### 4. 造接口（输入/输出契约）

写清参数名、类型、必填性、示例值；写清输出格式（固定 Markdown 结构或 JSON）。这让技能可被其他技能/脚本稳定调用。

### 5. 勤复盘（可迭代）

技能是产品：把真实 Bad Case 反向补成规则或反例，而不是每次重新解释。

## 写作步骤

1. **收样本**：收集 3-5 个真实请求，找出它们的共同点与分歧点。
2. **定边界**：写一句「本技能做什么」，再写一句「本技能不做什么」。
3. **定产物**：先确定输出长什么样（模板/字段/验收标准），再写步骤。
4. **写正文**：按「何时用 → 心智模型 → 步骤 → 红线 → 示例 → 自检清单」组织。
5. **压长度**：删掉模型本来就知道的通识；只留**本领域特有**的判断与坑。
6. **试跑**：用一个真实请求跑一遍，记录跑偏点，回填红线或反例。

## 正文骨架（可直接套用）

```markdown
# <技能名>

## 何时用 / 何时不用
## 输入与输出契约
## 步骤（编号，每步含产物）
## 红线（禁止事项）
## 示例（1 好 1 坏）
## 自检清单（提交前逐条打勾）
```

## 常见失败模式

| 症状 | 根因 | 修法 |
| --- | --- | --- |
| 技能从不被选中 | description 太抽象（「一个数据处理工具」） | 写具体场景与触发词，含用户会说的原话 |
| 选中了但执行乱 | 正文只有原则没有步骤 | 补编号步骤与每步产物 |
| 输出格式不稳定 | 没有输出契约 | 固定模板/JSON schema，给示例 |
| 技能生效但看不到效果 | 模型没拿到所需工具 | 在正文写清「需要哪些工具/命令」，并确认工具可用 |
| 同类任务偶发失败 | 缺反例 | 把失败样本写成坏例子并标差异 |

## 自检清单

- [ ] name 与目录名一致，description 含场景 + 触发 + 产出
- [ ] 正文单一职责，出现第二个「并且」已拆分
- [ ] 有编号步骤，每步写明产物
- [ ] 有红线，明确禁止编造与越权
- [ ] 有 1 好 1 坏示例
- [ ] 有输入/输出契约
- [ ] 长资料已移到 references/，正文只留索引
- [ ] 正文 < 5000 token
