# 规则（Rules）编写与排查

## 规则、技能、智能体怎么选

| 想要的效果 | 用哪个 | 判断 |
| --- | --- | --- |
| 每轮都必须遵守的**约束**（语言、风格、技术栈、禁止事项） | 规则 | 内容短、跨任务、无需判断 |
| 一类任务的**多步流程** | 技能 | 需要读文档、调工具、按 SOP 走 |
| 某个角色的**专长人设** | 自定义智能体 | 需要独立上下文与职责边界 |
| 一次性的**固定指令** | 直接输入 | 不复用 |

口诀：**规则管「不许怎样」，技能管「怎么一步步做」，智能体管「谁来做」。**

## 规则的两层作用域

- **个人规则**：跨项目生效，放语言偏好、代码风格、工具偏好（如「用 pnpm 不用 npm」「回答用中文」）。
- **项目规则**：只对当前项目生效，放架构约定、目录结构、命名、测试与提交规范。

两者冲突时：**项目规则优先**（更具体）。不要把项目专属内容写进个人规则，否则换个项目全是噪音。

## 编写方法

1. **一条规则一个约束**：一句话能被判定真假。反例「代码要优雅」不可判定。
2. **写成祈使句 + 可验证标准**：反例「注意性能」→ 正例「列表渲染必须虚拟化，超过 100 行不得一次性渲染」。
3. **同类合并**：命名、注释、错误处理各成一组，避免同一条规则出现三次。
4. **控制总量**：规则越长，单条权重越低。**宁可 20 条硬约束，不要 100 条软建议。**
5. **语言选择**：英文规则在多数模型上遵循度更稳；面向中文团队的可读性需求可用中文，但术语保持英文。
6. **写清优先级**：在规则头部写明「与安全策略冲突时以安全策略为准」，避免模型在冲突时乱选。

## 规则模板

```markdown
# 项目规则

## 语言与沟通
- 回答使用中文；代码标识符用英文。
- 不确定就说不确定，禁止编造未验证的事实。

## 技术栈
- 前端 Vue 3 + TypeScript；后端 Rust。
- 包管理器使用 pnpm，禁止 npm install。

## 编码
- 每个公开函数必须有文档注释，说明输入/输出/失败条件。
- 错误必须显式处理；禁止 `unwrap()` 处理用户输入。

## 验证
- 提交前必须通过：构建、测试、静态检查。
- 未实际运行的验证不得声称通过。

## 禁止
- 不得删除用户未提交的改动。
- 不得把密钥写入源码或日志。
```

## 「规则写了却不生效」排查顺序

1. **作用域错**：写进了个人规则但内容只适用于一个项目 → 移到项目规则。
2. **冲突**：与另一条规则或系统策略冲突，模型自行取舍 → 删掉弱的那条。
3. **过长**：规则总量过大被稀释 → 砍到 20-30 条以内，长的挪进技能。
4. **不可判定**：「尽量」「注意」「优雅」这类词无法执行 → 改成可验证标准。
5. **放错层**：这是流程而不是约束 → 改写成技能，由模型在触发时加载。
6. **未重载**：改完未重启/未刷新规则缓存 → 确认规则已重新加载。

## 从现有文档生成规则

把团队规范文档交给模型，用固定指令：

```text
把这份文档聚合成项目规则：只保留可判定的约束，合并重复项，
按「语言/技术栈/编码/验证/禁止」分组，总长控制在 30 条以内，
无法判定的条目列在末尾待人工确认。
```

## 代码坏味道与重构约束（可直接作为项目规则片段）

| 坏味道 | 判定信号 | 处理方向 |
| --- | --- | --- |
| 神秘命名 | 需要注释才能看懂变量含义 | 重命名为意图名 |
| 重复代码 | 同一逻辑出现 3 次以上 | 提取函数/模块 |
| 过长函数 | 超过一屏或含多层嵌套 | 按步骤拆分 |
| 过大结构体 | 字段按不同场景分组 | 拆成多个内聚结构 |
| 过长参数列表 | 参数 > 4 个 | 引入参数对象 |
| 发散式变化 | 一处需求改动碰多个不相关文件 | 按变化原因重划边界 |
| 霰弹式修改 | 一个改动要在十几个文件重复改 | 收敛到单点 |
| 依恋情结 | 方法大量访问别的对象数据 | 移动方法到数据所在处 |
| 数据泥团 | 几个字段总是一起出现 | 合成对象 |
| 基本类型偏执 | 用字符串表达有结构的值 | 引入类型/枚举 |

重构纪律：**小步、每步可运行、每步有测试、每步可回滚**。

## 自检清单

- [ ] 每条规则可判定真假
- [ ] 总量 ≤ 30 条，长内容已移到技能
- [ ] 作用域正确（个人 vs 项目）
- [ ] 无相互冲突条目
- [ ] 写明与安全策略的优先级
- [ ] 改完后确认已重新加载
