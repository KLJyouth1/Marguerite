# 先计划再执行

## 何时必须先做计划

- 改动跨 3 个以上文件或跨层（前端 + 后端 + 契约）
- 涉及数据库迁移、接口契约变更、破坏性重构
- 需求描述含糊，存在多种合理解读
- 预计执行超过 10 个步骤

小改动（单文件、单函数、明确 bug）不要走这套流程，直接做并验证。

## 计划必须包含的六件事

1. **目标**：一句话，可判定成败。
2. **验收标准**：3-5 条，每条都能用命令/观察验证。
3. **影响面**：要改哪些文件/模块/接口，哪些**不改**。
4. **步骤**：每个步骤的输入、动作、产物、验证方式。
5. **风险与回滚**：最坏情况是什么，怎么退回去。
6. **未决问题**：需要用户拍板的点，先问再动手。

缺任何一项的计划都是假计划。**没有验收标准的计划不要执行。**

## 步骤粒度

好的步骤：**能在一次专注内完成，且完成即可验证**。

- 太大：「实现后端」→ 无法验收
- 太小：「加一个 import」→ 噪音
- 合适：「新增 `rules` 模块 + 4 个 RPC + 契约三处同步，用 `cargo check` 验证」

## 待办与节奏

1. 计划确认后再建待办，顺序即执行顺序。
2. 每完成一项立即标记，不等一批做完。
3. 每 2-3 项做一次中间验证（编译/测试），不要攒到最后一次跑。
4. 出现阻塞立刻记录并调整后续顺序，不静默跳过。

## 并行

可并行的判据：**互不写同一文件、互不依赖对方产物**。

```text
可并行：前端页面 + 后端模块（接口契约先定死）
不可并行：契约定义 → 前端接线 → 后端实现（有顺序依赖）
```

并行时要注意：共用工作区会被同时写入，冲突时先看文件修改时间与进程，不要假定是自己改坏的。

## 执行期的三条纪律

1. **先读后改**：没读过文件不许编辑，没跑过的验证不许声称通过。
2. **小步提交**：每步可编译、可回滚；不把多个不相关改动混在一起。
3. **证据优先**：完成声明必须附命令与输出，不采信「应该没问题」。

## 收尾验收

| 检查 | 要求 |
| --- | --- |
| 功能 | 验收标准逐条对照，未过的写清原因 |
| 回归 | 相关测试全绿，新增逻辑有对应用例 |
| 静态检查 | 编译零警告、静态检查零新增告警 |
| 契约 | 前后端字段/方法名一致 |
| 遗留 | 未完成项与已知缺陷显式列出，不藏 |

## 常见失败模式

| 症状 | 根因 | 修法 |
| --- | --- | --- |
| 做完发现方向错 | 计划缺少验收标准 | 先写验收再写步骤 |
| 改一处崩三处 | 影响面没列全 | 先搜引用点，列出受影响文件 |
| 越做越乱 | 步骤粒度太粗 | 拆到「一次专注可完成」 |
| 返工多次 | 未决问题没先问 | 把阻塞问题前置到计划阶段 |
| 声称完成但没验证 | 无证据纪律 | 每步附命令输出 |

## 自检清单

- [ ] 目标与验收标准可判定
- [ ] 影响面含「不改什么」
- [ ] 每步有产物与验证方式
- [ ] 风险与回滚已写
- [ ] 未决问题已确认
- [ ] 并行任务无文件冲突
- [ ] 收尾附新鲜证据
