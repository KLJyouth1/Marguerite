# 前端开发规范 v1.0 — Marguerite（双原生前端）

> 版本：v1.0
> 生效日期：2026-08-07
> 依据：对 `desktop/`（egui）、`tui/`（ratatui）以及 `core/src/tui/` 的实际代码勘察、`Orchestrator` 公共 API（`analyze` / `dispatch`）实测调用链、`cargo build -p marguerite-tui -p marguerite-desktop` 门禁通过。
> 适用范围：Marguerite 两个原生前端 crate。全程无 git 操作。

---

## 1. 前端定位与红线

- **双原生，零 Web / 零 WebView**：桌面用 `egui`（eframe），终端用 `ratatui`（crossterm）。单一原生二进制，不引入任何浏览器渲染层。
- **渲染与逻辑分离**：前端**只做渲染**，所有业务逻辑（编排、能力、安全、记忆）只在 `core`（Rust）。前端不得重写业务规则。
- **零用户编排 UI（硬性红线）**：前端**不得**提供任何让用户手动选择「编排形态（Solo / MAX / 专家团队 / 集群）/ 操轮子 Agent」的控件。形态**只能由引擎 `Orchestrator::analyze()` 自动得出**，前端只读展示 `strategy_label` 与 `strategy_rationale`。
- **能力面 SSOT**：能力树来自 `core/src/domain/capabilities.rs` 注册表（`by_group()` / `stats()`）。GUI / TUI / CLI 三前端共读同一份，禁止各前端硬编码能力列表或「超集/子集」差异。

---

## 2. 离线优先与优雅降级（强制）

引擎有两条路径，前端必须同时处理好：

| 路径 | 触发 | 引擎行为 | 前端职责 |
|------|------|----------|----------|
| 离线回显 | 无 API Key（`config.model.api_key` 为空） | `analyze()` 纯规则判定形态；`dispatch()` 无后端 | 展示「离线模式」提示 + 自动编排形态（只读）+ 回显用户输入 |
| 在线执行 | 有 API Key | `analyze()` 判定形态 → `dispatch()` 接 LLM 出真回复 | 转发输入到引擎线程，回流 `lead_reply` |

**判定方式（已实测）**：`desktop/src/main.rs` 通过 `Config::load().model.api_key.trim().is_empty()` 决定 `online` 标志；`tui` 同理在 `App::on_submit` 离线分支调 `Orchestrator::analyze` 回显。

> 红线：离线分支**只能展示**，不得伪造「AI 回复」。离线回显文案须明确标注「[离线回显]」，避免误导用户以为已调模型。

## 3. 调用链约定（两前端统一）

```
用户输入
  │
  ▼
Orchestrator::analyze(&text)        // 离线，永远可用：返回 TaskAnalysis{ strategy, rationale }
  │  → 前端只读展示 strategy_label / strategy_rationale（用户不可改）
  ▼
（online 时）Orchestrator::dispatch(&text).await   // 接 LLM 后端
  │  → OrchestrationOutcome{ lead_reply, ... }
  ▼
前端渲染 lead_reply / 错误
```

- **桌面端（已实测，`desktop/src/main.rs`）**：`Orchestrator` 跑在独立 `std::thread` + `tokio::runtime` 内；UI 线程经 `mpsc` 发输入、收 `GuiMsg::{Reply, Strategy, Error}`，`update()` 中非阻塞 `try_recv()` 回流，避免阻塞渲染。
- **终端端（已实测，`tui/src/main.rs` → `core/src/tui/app.rs`）**：`App::new().run()` 进入 crossterm/ratatui 终端循环；`on_submit` 离线分支调 `analyze` 回显，在线分支调 `dispatch`。

**新增前端（如未来移动端）必须复用同一条 `analyze → dispatch` 链，且不得新增「形态选择」UI。**

## 4. TUI（ratatui）规范

- **入口**：`tui/src/main.rs`：`App::new().run()`。`App` 定义在 `core/src/tui/app.rs`（566 行），`run()` 内含完整终端事件循环。
- **模块结构**：`core/src/tui/{app,chat,mod}.rs` + `workbench/`（9 文件，含 `region/` 7 文件）+ `bloom/`（6 文件）。`workbench` 是主工作台布局，`bloom` 是双模型可视化。
- **事件处理**：用 `crossterm::event` 读键盘/resize；`on_submit` 处理输入发送。异步调用 `dispatch` 须用 `tokio::spawn` 或后台任务，禁止在终端循环里 `block_on` 长时间阻塞（会卡 UI）。
- **布局原则**：左/上栏展示能力树（来自 `by_group()`），中栏对话，底栏输入。布局须适配终端尺寸变化（ratatui `Layout` 响应式）。
- **测试**：`core/src/tui/app.rs` 的 `test_on_submit_flow` 须随离线行为同步——断言离线消息含「自动编排判定」+「[离线回显]」，而非旧版「API Key」文案。改离线行为时**必须**同步改该测试。

---

## 5. 桌面（egui）规范

- **入口**：`desktop/src/main.rs`（240 行）：`eframe::run_native("Marguerite", ..., Workbench::default())`。`Workbench` 实现 `eframe::App::update()`。
- **线程隔离（强制）**：引擎（`Orchestrator` + tokio runtime）**必须**跑在独立 `std::thread`，不得在主 UI 线程 `block_on` 引擎（egui `update` 需每帧返回）。已实测模式：`thread::spawn` 内建 `tokio::Runtime`，`mpsc` 桥接。
- **左栏能力树**：`egui::SidePanel::left` 渲染 `by_group()`，按 `CapabilityTier` 打「独家/增强/基线」标签，体现能力面规模（SSOT）。
- **中栏对话工作台**：只读展示「自动编排」形态（`strategy_label`），明确文案「编排形态由 agent 自动决定，无需手动选择」。离线时 `colored_label` 橙色提示。
- **无 WebView / 无 HTML**：所有控件用 egui 原生 widget；不得内嵌任何 web 渲染。

---

## 6. UI 设计约束（继承项目 P0 规则精神）

虽为原生 UI（无 web 颜色硬编码），仍须遵守项目级反模板原则：

1. **禁止 emoji 作功能图标**：图标用统一描边 SVG / 字体图标方案，杜绝 emoji 充图标。
2. **禁止紫粉渐变主视觉**：不得 `linear-gradient(135deg, #7C3AED→#A855F7→#EC4899)` 及 Indigo→Pink 渐变 + 发光边框 + 毛玻璃三位一体 AI 模板套路。
3. **禁止 AI 模板味文案**：不得「Welcome to Our App」/「Sign up today」类空洞占位；离线提示、错误提示须是具体中文业务文案。
4. **配色克制一致**：三前端共享一套语义色（成功/警告/错误/中性），不每前端各搞一套。
5. **零手动编排控件**（重申红线）：任何「选 Solo / MAX / 专家 / 集群」的下拉、按钮、开关均禁止。

---

## 7. 测试与构建门禁

- **构建门禁（强制）**：`cargo build -p marguerite-tui -p marguerite-desktop` 必须 EXIT 0。新增前端代码不得破坏。
- **逻辑测试**：业务判定逻辑尽量下沉 `core`，在 `cargo test -p marguerite-core` 守护（当前 899 用例）。前端 crate 自身以 build + 必要单元测试（如 `test_on_submit_flow`）为主。
- **无 headless 集成测试要求**：终端/桌面渲染不强制自动化 UI 测试（原生 UI 难 headless），但**引擎调用链（`analyze`/`dispatch`）必须在 core 层有测试覆盖**。

## 9. 后续调整规划

| 优先级 | 项 | 说明 |
|--------|----|------|
| P1 | 统一三前端能力树渲染组件 | GUI/TUI/CLI 共抽一个 `capability_tree_view`，避免各前端各写一遍 `by_group` 遍历 |
| P1 | 离线回显文案规范化 | 统一「[离线回显]」前缀与「自动编排形态」展示格式，两前端一致 |
| P2 | 流式回复（streaming） | `model/llm.rs` 已有 `chat_complete_stream`；前端接 `StreamReceiver` 做增量渲染 |
| P2 | 错误分类展示 | `GuiMsg::Error` 区分「引擎错误 / 网络 / 护栏拒绝」，前端差异化提示（尤其 L2/L3 拒绝原因） |
| P3 | 移动 / Web 前端（如需） | 必须复用同一条 `analyze → dispatch` 链，且不得新增形态选择 UI |

## 附录 A：前端禁止清单（速查）

- ❌ 任何「手动选择编排形态 / Agent」的控件
- ❌ 前端内重写业务规则（安全/记忆/编排）
- ❌ 硬编码能力列表（必须读 `capabilities` 注册表）
- ❌ emoji 功能图标、紫粉渐变主视觉、AI 模板味文案
- ❌ 在主 UI 线程 `block_on` 引擎（egui）/ 在终端循环长阻塞（ratatui）
- ❌ 伪造「AI 回复」（离线只能展示回显，须明确标注）
