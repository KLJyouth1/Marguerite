# 后端开发规范 v1.0 — Marguerite（UnivAgent 整合引擎）

> 版本：v1.0
> 生效日期：2026-08-07
> 依据：对 `marguerite/` 工程的实际代码勘察（`cargo test` 实测 899 用例 EXIT 0、双前端 `cargo build` 门禁通过）、`docs/capability-reconciliation.md` 能力对账、以及逐模块桩代码甄别结果。
> 适用范围：`marguerite/` Rust 单引擎（`core` crate）+ 双原生前端（`desktop`/`tui` crate）。全程无 git 操作。

## 0. 本规范与对账文档的关系

`docs/capability-reconciliation.md` 是「叙事 vs 真货」的对账清单；本规范是「**怎么在这个代码库上继续开发**」的硬性标准。本规范第 2 节的判定修正，是对账文档在 2026-08-07 代码实测后的**二次校准**——对账文档曾把若干已实装模块误判为纯叙事（⚪），本规范据实测纠正。

---

## 1. 工程定位与核心约束

- **单引擎 + 双原生前端，零 Web**：所有能力逻辑只在 `core`（Rust）实现，桌面（egui）与终端（ratatui）只做渲染，不重复实现业务。
- **离线优先（offline-first）**：`Orchestrator::analyze()` 是纯规则引擎，**不依赖任何 LLM / API Key** 即可运行（自动判定编排形态 Solo / MAX / 专家团队 / 集群）。`Orchestrator::dispatch()` 才接真实 LLM 后端，无 Key 时降级。
- **零用户编排 UI**：前端不得提供任何让用户手动选择「编排形态 / 操轮子 Agent」的控件。形态**只能由引擎 `analyze` 自动得出**，前端只读展示 `strategy_label` / `strategy_rationale`。
- **能力面 SSOT**：能力树来自 `core/src/domain/capabilities.rs` 注册表（`by_group()` / `stats()`），GUI / TUI / CLI 三前端共读同一份，禁止各前端硬编码能力列表。

## 3. 分层架构与目录职责

```
marguerite/
├── Cargo.toml              # workspace: members = [core, desktop, tui]
├── core/                   # Rust 单引擎（所有业务逻辑）
│   └── src/
│       ├── lib.rs          # 顶层 re-export（capabilities / orchestration / tui ...）
│       ├── domain/         # 领域模型 + capabilities.rs 能力注册表（SSOT）
│       ├── orchestration/  # Orchestrator：analyze(离线规则) + dispatch(在线LLM)
│       ├── model/          # LLM 集成层（llm/router/dual/bloom/byok）—— 🟡 需 Key
│       ├── agent/          # 子代理 / tool_cycle
│       ├── chain/          # 调用链执行器（ChainExecutor）—— ✅ 框架，部分内置桩
│       ├── collab/         # 协作原语（auth/conflict/session/workspace）—— ✅
│       ├── sandbox/        # 命令执行沙箱（白名单/逃逸拦截/路径守卫/审计）—— ✅
│       ├── security/       # L1 command/exec/ssrf + L2 malware + L3 guardrail —— ✅
│       ├── mcp/            # MCP client/server/registry —— 🟡 部分方法未实现
│       ├── deploy/         # SSH/Baota 一键部署 —— ✅
│       ├── kb/             # RAG + graph + denoiser + integrity —— ✅
│       ├── research/ vision/ automation/  # 离线降级能力 —— ✅
│       ├── memory/ governance/ recovery/   # 记忆 / 治理双闭环 / 快照 —— ✅
│       ├── tools/          # exec/file/rollback 工具执行 —— ✅
│       ├── tui/            # ratatui 前端逻辑（App::run）+ workbench/bloom
│       ├── serve/          # ACP 回环 listener（仅 mod.rs 挂载，实现在 serve/acp/）
│       └── cli/ intent/ guard/ mode/ session/ events/ context/ persistence/ plugins/ skills/
├── desktop/                # egui 原生桌面前端（eframe::App）
└── tui/                    # ratatui 终端前端 bin crate（App::new().run()）
```

**分层依赖规则**（防止环形依赖与逻辑下沉）：
- `domain` 不依赖任何上层；`orchestration` 依赖 `domain` + 各能力模块；前端只依赖 `orchestration` + `domain`，**不得**直接依赖 `chain`/`sandbox` 等内部实现细节。
- 能力模块（research/vision/kb/security…）通过 `orchestration` 暴露的 `set_*` 注入点（如 `set_research_llm` / `set_vision_resolver`）解耦，便于测试 mock。

## 4. 编码规范（强制）

1. **错误处理**：统一 `anyhow::Result` 向上传播；库内部不 `unwrap()` 生产路径（测试/示例除外）。异步用 `tokio`。
2. **可测性注入**：对外部副作用（进程执行、网络、文件系统）抽象为 `trait` 并允许注入 mock。范例：`sandbox::CommandRunner`（测试用 `RecordingRunner`），`deploy::SshTransport`（`RecordingTransport`）。**新增带副作用的模块必须提供可注入 trait**，否则测试门禁打回。
3. **内部可变性**：跨 `await` 持有状态用 `Arc<Mutex<T>>` / `Arc<Mutex<KnowledgeBase>>`，**先 clone 出锁再跨 await**，避免 `MutexGuard` 非 `Send`。
4. **模块组织**：每个能力模块 = `mod.rs`（公开 API + re-export）+ 子文件（实现）。`mod.rs` 顶部 `//!` 文档必须写明「本模块做什么、 fail-closed 行为、测试入口」。
5. **零警告门禁**：`cargo build` / `cargo test` 不允许新增 `warning`（既有 `uuid unused` / `dead_code` 等旧 warning 也应在相关改动时清理）。
6. **命名**：模块内类型 `PascalCase`，文件 `snake_case`，测试函数 `snake_case` 且覆盖「正常 / 边界 / 失败」。
7. **正则注意**：`regex` crate **不支持 look-ahead `(?!...)`**（曾致 `Regex::new` 运行时 panic）；含字面 `"` 的原始字符串须用 `r#"..."#` 而非 `r"..."`。

## 5. 能力接入规范（杜绝「宣称未落地」）

新增能力必须走四步，**任一步缺即视为未完成**：

1. **登记注册表**：在 `domain/capabilities.rs` 的 `build_capabilities()` 加条目（`tier` = Baseline/Enhanced/Exclusive），并**同步补充 `implemented` 落地标志**（见第 8 节规划）——让「叙事 vs 真货」可机器校验。
2. **实现模块**：在 `core/src/<cap>/` 落地真实逻辑（非桩）。
3. **接线编排器**：通过 `Orchestrator` 的 `set_*` 注入或 `dispatch` 分支暴露；离线 `analyze` 若涉及该能力须有规则判定。
4. **测试守护**：至少在模块内加 `#[test]` / `#[tokio::test]`，跑通 `cargo test -p marguerite-core` 零回归。**无测试的能力不计入「已实装」**。

> 历史教训：`capabilities.rs` 此前仅有 `tier` 叙事字段、无 `implemented` 标志，导致 research/vision/automation/serve/KB/security 等曾被标 Exclusive 却长期零实现。本规范强制四步闭环。

## 6. 治理双闭环（强制接入）

- **PlanGate（执行前）**：宪法 C1–C4 约束在 `dispatch` 前校验，未过即拒。
- **CompletionGate（产出后）**：四检查 + 自报文件落盘核验；产出物须经 `evaluate_completion()`。
- 新增「会改变文件 / 执行命令 / 调网络」的能力，**必须**经过 `security` 三层（L1 命令/执行/SSRF → L2 恶意码扫描 → L3 权限边界）与 `sandbox` 命令沙箱。

---

## 7. 安全分层规范

| 层 | 模块 | 职责 | 落地 |
|----|------|------|------|
| L1 | `security/{command_guard,exec,ssrf_guard}` | 命令护栏 / 执行沙箱 / SSRF | ✅ |
| L2 | `security/scanner_l2` | 恶意代码静态扫描（`sec.malware`：eval/exec 注入、反向 shell、凭证泄露、破坏性、不安全反序列化、路径穿越） | ✅ |
| L3 | `security/scanner_l3` | 操作护栏（`sec.guardrail`：系统/凭证目录、`.git`、沙箱逃逸意图、跨工作区/ `..` 穿越） | ✅ |
| 命令沙箱 | `sandbox/` | 白名单三分法 + 解释器逃逸拦截 + 路径守卫 + 超时 kill + JSONL 审计 | ✅ |
| OS 级隔离 | `sec.os_sandbox` | Landlock/Seatbelt 系统调用隔离 | ⚪（待重型原生实现） |

**铁律**：任何「执行命令 / 写文件 / 调网络」路径，先过 `sandbox` 判定层，再叠加 `security` L1–L3 扫描。fail-closed：判定层返回 `None`（放行）以外的任何值都视为拒绝。

## 8. 测试与质量门禁

- **单元/集成**：`cargo test -p marguerite-core` → 当前 **lib 893 passed + e2e 5 + perf 1 = 899 用例，EXIT 0，零回归**。新增代码不得破坏该基线。
- **前端 build 门禁**：`cargo build -p marguerite-tui -p marguerite-desktop` 必须 EXIT 0。
- **桩代码标记**：未实现的工具/方法必须用 `code: "NOT_IMPLEMENTED"` 或显式 `// STUB: <原因>` 标注（参考 `chain/builtin.rs`），**严禁**静默返回空成功。CI 应统计 `NOT_IMPLEMENTED` 数量趋势。
- **异步 TCP 测试**：tokio 下写网络端到端测试，客户端必须用 `tokio::net::TcpStream`（异步），**绝不用**同步 `std::net::TcpStream`（会阻塞 runtime worker，单核环境致 accept 饿死、连接超时 code 10060）。
