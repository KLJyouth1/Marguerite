## 2. 核心方法论：双向观察闭环（每一步都走完）
**A. 前台动作驱动**
1. 前台执行某功能（如「发布商品」）。
2. 立即切后台：打开对应管理页（商品管理），确认记录出现且状态正确。
3. 抓 API：记录该动作触发的路由（如 `/index.php?...`）、请求参数、响应码与报文。
4. 查 DB：`SELECT` 对应表，确认字段写入正确（状态、金额、时间、外键）。
5. 回前台：刷新对应页面，确认 UI 状态与后台/DB 一致（无延迟、无错乱）。
6. 判定「完美」或记录缺陷（带证据）。

**B. 后台动作驱动**
1. 后台执行某操作（如「通过学生认证」）。
2. 立即切前台：登录对应账号，确认状态变化（如「已认证」徽章、获得开店/发布权限）。
3. 抓 API + 查 DB，确认变更已落库。
4. 判定前后台一致性。

> 铁律：每次前后台切换都重新抓 API/DB 对账，**不凭记忆**。

## 3. 测试矩阵（按优先级执行，每格走完闭环）
- **A 用户生命周期**
  - A1 注册（手机/邮箱）→ 登录 → 退出 → 密码找回
  - A2 学生身份认证（提交资料）→ 后台审核通过 → 前台权限变化（可开店/可发布）
  - A3 开通不同身份卖家（个人/商家）→ 开店 → 后台店铺审核 → 前台店铺页可见
- **B 交易主链路**
  - B1 充值（模拟支付）→ 余额变动 → 后台资金流水
  - B2 发布商品 → 后台商品管理可见
  - B3 咨询（留言/IM）→ 后台会话/消息
  - B4 议价（还价→接受）→ 价格变更双向同步
  - B5 下单 → 支付（余额/第三方）→ 订单状态机正确 → 后台订单可干预
- **C 租赁 / 竞拍**
  - C1 发布租赁商品 → 租期/押金逻辑
  - C2 发布竞拍 → 出价 → 倒计时/成交 → 支付 → 订单
- **D 店铺管理**
  - D1 店铺工作台（数据看板）
  - D2 商品 / 订单 / 售后管理
  - D3 信誉体系（评价→信誉分变化→前台展示）
- **E 后台管控**
  - E1 用户 / 认证审核队列
  - E2 商品管控（下架 / 禁售 / 敏感词）
  - E3 订单干预（改价 / 退款 / 发货）
  - E4 店铺管控
  - E5 内容 / 风控规则配置
- **F 风控专项**

## 4. 「完美」判定清单（每条用例逐项勾选）

- [ ] API 正确（路由存在、参数合法、响应码 2xx、报文结构正确）

- [ ] 无报错（前端 console、后端 error log 干净）
