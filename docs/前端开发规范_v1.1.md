# 通用前端开发规范 v1.1（用户通用标准 · 含 Marguerite 实战案例）

> 版本：v1.1（由 v1.0 项目专属版升格为用户通用标准）
> 生效日期：2026-08-07
> 性质：**本规范是「用户通用前端工程标准」**，不绑定任何框架/平台（Web / 桌面原生 / 终端 TUI / 移动端皆可套用）。第 1–7 节为普适纪律；每节末尾「Marguerite 案例」用双原生前端（egui + ratatui）展示落地。第 8 节为门禁速查。
> 适用范围：任何带 UI 的前端工程，尤其是「前端 + 后端引擎」分离架构。
> 约束：本规范不规定具体 UI 框架，只规定**架构与质量标准**；选型由前端架构师按平台决定。

---

## 0. 如何使用本规范

- **普适原则**（第 1–7 节）= 强制纪律，适用于 Web / 桌面 / TUI / 移动端。
- **Marguerite 案例** = 同一纪律在「egui 桌面 + ratatui 终端」双原生前端的落地方式。
- **第 8 节自查清单** = 交付前门禁。

---

## 1. 渲染与逻辑分离（SSOT）

**原则**：前端**只做渲染**，所有业务逻辑（编排、能力、安全、记忆、状态判定）只在后端/核心引擎实现。前端**不得重写业务规则**，也不得在各前端各存一份「能力列表 / 状态机」。

落地点：
- 核心引擎是唯一事实源（SSOT）；前端通过引擎暴露的公开 API（如 `analyze` / `dispatch`）读取状态。
- 三前端（Web / 桌面 / 终端）共读同一份能力树/状态，禁止硬编码或各搞「超集/子集」差异。

**Marguerite 案例**：所有业务逻辑只在 `core`（Rust）；`desktop/`（egui）与 `tui/`（ratatui）只渲染。能力树来自 `core/src/domain/capabilities.rs` 注册表（`by_group()` / `stats()`），GUI / TUI / CLI 三前端共读。

---

## 2. 离线优先与优雅降级（UI 只展示，不伪造结果）

**原则**：引擎有「离线 / 在线」两条路径，前端必须同时处理好：

| 路径 | 触发 | 引擎行为 | 前端职责 |
|------|------|----------|----------|
| 离线 | 无 API Key / 无后端 | 纯规则判定形态；不接 LLM | 展示「离线模式」+ 自动判定结果（只读）+ 回显用户输入 |
| 在线 | 有 API Key / 后端就绪 | 接 LLM / 后端出真回复 | 转发输入到引擎线程，回流真实回复 |

- **红线**：离线分支**只能展示**，不得伪造「AI 回复」。离线回显文案须明确标注（如 `[离线回显]`），避免误导用户以为已调模型。

**Marguerite 案例**：`desktop/src/main.rs` 通过 `Config::load().model.api_key.trim().is_empty()` 决定 `online` 标志；`tui` 离线分支调 `Orchestrator::analyze` 回显，在线分支调 `dispatch`。

---

## 3. 设计反模板（继承项目 P0 规则精神）

**原则**：无论 Web 还是原生 UI，都须遵守反模板原则，杜绝「AI 生成味」：

1. **禁止 emoji 作功能图标**：图标用统一描边 SVG / 字体图标方案，杜绝 emoji 充图标（语义模糊、跨平台渲染不一致）。
2. **禁止紫粉渐变主视觉**：不得 `linear-gradient(135deg, #7C3AED→#A855F7→#EC4899)` 及 Indigo→Pink 渐变 + 发光边框 + 毛玻璃三位一体 AI 模板套路。
3. **禁止 AI 模板味文案**：不得「Welcome to Our App」/「Sign up today」类空洞占位；提示/错误文案须是具体业务文案（最好本地化）。
4. **配色克制一致**：多前端共享一套语义色（成功/警告/错误/中性），不每前端各搞一套主题。

**Marguerite 案例**：虽为原生 UI（无 web 颜色硬编码），仍遵守上述原则；离线提示用橙色 `colored_label` 显式区分，不套 AI 模板文案。

---

## 4. 形态自动判定，UI 只读（不让用户手动选 Agent / 编排）

**原则**：系统的「编排形态 / 选哪个子 Agent / 走哪条执行轨道」**只能由引擎自动判定**，前端**不得**提供任何让用户手动选择的控件（下拉、按钮、开关、单选）。

- 前端只读展示引擎给出的形态标签与理由（`strategy_label` / `strategy_rationale`），用户不可改。
- 理由：形态选择是业务逻辑，放前端易产生「用户误配导致能力失效」的故障面，也破坏「引擎是 SSOT」。

**Marguerite 案例**：前端零「选 Solo / MAX / 专家 / 集群」控件；`strategy_label` 由 `Orchestrator::analyze()` 自动得出，前端只渲染「编排形态由 agent 自动决定，无需手动选择」。

---

## 5. 能力面 SSOT（不硬编码）

**原则**：前端展示的能力树 / 特性列表**必须来自后端注册表**，不得在前端硬编码或写死「支持哪些能力」。

- 后端能力成熟度（Real/Partial/Narrative）变化后，前端自动反映，无需改前端代码。
- 禁止前端对能力做「超集/子集」差异化裁剪（那是后端职责）。

**Marguerite 案例**：`egui::SidePanel::left` 渲染 `by_group()`，按 `CapabilityTier` 打「独家/增强/基线」标签；`tui` 左栏同样读 `by_group()`。后端加 `tool.git` 标 `Real`，前端无需改动即显示。

---

## 6. 线程隔离（引擎不在 UI 线程同步阻塞）

**原则**：耗时引擎（LLM 调用、编排、重计算）**必须**跑在独立线程 / 异步运行时，**绝不在主 UI 线程 `block_on` 长时间阻塞**（会卡 UI、掉帧、甚至无响应）。

- 引擎线程经消息桥（mpsc / channel）与 UI 线程通信，UI 侧非阻塞 `try_recv()` 回流。
- 异步调用须用 `spawn` / 后台任务，禁止在渲染循环里长阻塞。

**Marguerite 案例**：`desktop` 引擎跑在独立 `std::thread` + `tokio::Runtime`，UI 线程 `update()` 内 `try_recv()` 回流 `GuiMsg::{Reply, Strategy, Error}`；`tui` 在 `on_submit` 用 `tokio::spawn` 调 `dispatch`，不阻塞终端循环。

---

## 7. 测试与构建门禁

**原则**：
- **构建门禁**：`build`（各前端 crate）必须 EXIT 0，新增前端代码不得破坏。
- **逻辑下沉测试**：业务判定逻辑尽量下沉核心层，在核心层测试守护（如 `cargo test -p <core>`）。前端 crate 自身以 build + 必要单元测试为主。
- **引擎调用链必测**：`analyze` / `dispatch` 等关键链路必须在核心层有测试覆盖，前端离线行为变更时**必须**同步改对应测试。
- **无 headless 集成测试强制要求**：原生 UI（终端/桌面）难 headless，不强求自动化 UI 测试，但引擎链路的测试不可省。

**Marguerite 案例**：`cargo build -p marguerite-tui -p marguerite-desktop` 门禁；`core/src/tui/app.rs` 的 `test_on_submit_flow` 断言离线消息含「自动编排判定」+「[离线回显]」，改离线行为时同步改该测试。

---

## 8. 自查清单（门禁速查）

交付前逐条核对：

| # | 门禁项 | 通过标准 |
|---|--------|----------|
| 1 | 渲染/逻辑分离 | 业务规则只在核心层，前端只渲染 |
| 2 | 离线降级 | 无后端/Key 时优雅展示，不伪造结果（明确标注离线） |
| 3 | 设计反模板 | 无 emoji 图标 / 紫粉渐变 / AI 模板味文案；配色一致 |
| 4 | 形态只读 | 无「手动选编排/Agent」控件，形态由引擎自动判定 |
| 5 | 能力 SSOT | 能力树读后端注册表，无前端硬编码 |
| 6 | 线程隔离 | 引擎不阻塞 UI 线程（独立线程/异步 + 消息桥） |
| 7 | 构建/测试门禁 | 前端 build EXIT 0；引擎链路有测试覆盖 |

### 案例：Marguerite 前端能力对账（实测）

- ✅ `core.chat`（自然语言编码对话）：双原生前端 `cargo build` 通过；离线 `analyze` 回显 + 在线 `dispatch` 真实调用链实测存在。
- ✅ 双原生前端：已落地（`tui/` bin + `desktop/`），根 `Cargo.toml` members 含 `tui`，双端 build 门禁通过。
- ✅ `core.apply`（安全应用改动）：L1/L3 护栏落盘机制在 core，前端只读展示（前端无写盘逻辑，安全在 core）。
- ⚪ 前端相关重型桥（`tool.browser` / `tool.terminal` / `auto.uia` 的 UI 桥）：仍属重型原生 RPA，不在本轮（详见《通用后端开发规范》重型桥条款）。

### 附录 A：前端禁止清单（速查）

- ❌ 任何「手动选择编排形态 / Agent」的控件
- ❌ 前端内重写业务规则（安全/记忆/编排）
- ❌ 硬编码能力列表（必须读核心注册表）
- ❌ emoji 功能图标、紫粉渐变主视觉、AI 模板味文案
- ❌ 在主 UI 线程 `block_on` 引擎（egui）/ 在终端循环长阻塞（ratatui）
- ❌ 伪造「AI 回复」（离线只能展示回显，须明确标注）
