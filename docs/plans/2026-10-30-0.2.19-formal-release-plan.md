## 1. 本轮新发现的主工作流：W 组 · 写入放大（照 Codex 的病历照自己）

### 1.1 外部事实（一手，全部带日期，来自 openai/codex 公开 issue/PR）

- **主因是诊断日志，不是会话数据**：实测 21 天写盘 ~37 TB（线性外推 640 TB/年）；
  `logs_2.sqlite` 只留 1.2 GiB / 50 万行，但 AUTOINCREMENT 已到 **55.4 亿**——≈ 1 万倍的 insert-prune 空转。
  根因是日志汇**独立于 `RUST_LOG`** 硬编码 `Level::TRACE`，每个成功 WebSocket 事件落 3 条（原文 + OTel log + OTel trace）。
  （[#28224] 2026-06-14，#17320 早在 04-10 就报过 ~5 MiB/s）
- 官方在 0.142.0 用 #29432/#29457「Reduced persistent-log churn」削掉约 85%，0.143.0 又补一次漏判（#29599）；
  但「日志级别不可配」到 10 月仍是 open（#31132、#34291 绕过过滤 50–68 MB/天、**#58090（10-29）10 分钟内重复落 182 条完全相同的配置快照 —— 无 dedupe**）。
- **第二条战线才是我们该怕的**：#34061（子 agent rollout JSONL 单会话 3 分钟写 483 MB / 35 万条）、
  #41806（`~/.codex` 42 GB，`archived_sessions/` 28 GB、1145 个平铺 rollout、82 个 >100 MB，**归档从不清理也不压缩**）、
  #35401（插件目录缓存每次 `plugin/list` 全量重写，**64% 字节完全相同**，65 GB/天）、
  #35032（压缩后仍 80% 满 → 反复重压缩）、#37435（确认只有 `history.persistence/max_bytes`，**没有 rollout 保留策略**）。
- 传闻与事实分开：「桌面宠物导致 NVMe 物理损坏」（#54899）是单用户归因，维护者未确认；「剩余 15% 仍近百 TB/年」是媒体推算。
  **引用时按「社区实测 + 官方措辞」表述，不要写成定值。**

### 1.2 我们的对应事实（代码确证，`文件:行号`）

好消息先说：**我们没有 Codex 那个头号病灶**。CLI 日志只写 stderr、默认 `warn`、尊重 `RUST_LOG`
（`core/src/cli/program.rs:327-336`），不存在「独立于 RUST_LOG 的硬编码 TRACE 落 SQLite」。
我们的风险全在**数据落盘**这一侧，而且有一条比 Codex 更糟：

| ID | 病灶 | 证据 | 量级 |

### 1.3 任务（按可验证性排序，一次一个行为，先测试后实现）

- [ ] **W1｜`record_partial` 去抖（本轮收益最大的一条）**
  - 实测（2026-10-30，用例 `context::session::tests::windowed_flush_writes_orders_of_magnitude_fewer_bytes_than_per_frame`，
    一轮 **200 帧**流式回复 + 提交 entry + 回合清位，同一份文本、只差落盘时刻）：
    - **改前（逐帧落盘）＝202 次整档重写 / 952,987 字节**
    - **改后（≥1 s 窗口 + 边界必写）＝3 次 / 27,125 字节**
    - ⇒ **写入字节 −35 倍、次数 −67 倍**。对照组（202 次）也钉在同一个用例里，
      谁把去抖撤掉它就红，不需要有人重新手工测一遍。
  - 做法：内存里更新 `partial_text`，落盘按「≥ N ms 或 ≥ M 字节增长或回合结束」三条件之一触发；回合末 `clear_partial` 必落一次（崩溃恢复语义不变）。
  - 接口不变：`record_partial(session, text)` 签名与 `partial_text()` 读取口径不动，前端零改动。
  - 测试（先写失败测试）：① 连喂 200 帧 ⇒ 断言底层 `write_json_atomic` 次数 ≤ 阈值（需要一个可注入计数面，测试专用）；② 去抖窗口内 `partial_text()` 必须读到**最新**文本（内存优先，不许读到旧盘）；③ 回合结束必有一次落盘；④ 崩溃模拟：去抖窗口内进程被 kill ⇒ 下次 `partial_text()` 允许是旧值但**不能丢已提交的 entries**。
  - 变异：把条件判断反了 ⇒ ②红；把回合末落盘删了 ⇒ ③红。
  - 验收：同一 prompt、同一回复长度，**改动前后各跑一次**并给出写入字节数对比（真机或隔离网关，不许只报单测）。
- [ ] **W2｜`persist()` 增量化**：去掉 `to_string_pretty`（体积约 −25%，`session.rs:418`），并做「未变化则跳过」脏标——同仓已有范式 `cache/mod.rs:428 save_if_dirty`。
  - 关键红线：**记账顺序不能改**。引擎必须在发 `ToolResult` 事件**之前**登记幂等键（`context/session.rs:474-476` 明示），改异步/批量时若乱序 ⇒ token 双计。
- [ ] **W3｜三库开 WAL + `synchronous=NORMAL` + 保留 `busy_timeout`**：`sessions.db`、`usage.db`、`audit.db`。
  - 三条不可踩的坑：① Windows 上 `-wal/-shm` 被占用时 `PRAGMA journal_mode=WAL` 会**静默返回原模式** ⇒ 必须读回 `query_row("PRAGMA journal_mode")` 断言，别只看 execute 成功（`long_running.rs:735` 已有先例）；② 不许顺手删 `busy_timeout`——`usage/mod.rs:120-127` 注释记着 init 有 5+ 入口并发建表，无 timeout 时 `UsageLedger::new` 失败 ⇒ **进程内所有用量记录静默变 no-op**；③ 审计库的 ABORT 触发器**不动**。
- [ ] **W4｜有界化三件套**（直接复用现成原语 `observability/rotation.rs:90 rotate_if_oversized_with` / `:129 prune_dir_to_budget_with`，别再写第四份轮转）
  - ① `context/` 台账目录加**字节预算** + LRU 淘汰 + 启动时清理「无主 JSON」（会话已删但文件留下）；
  - ② `plans.json` 运行历史滚动裁剪（写线程已有合并快照 `plan/mod.rs:258-262`，只缺裁剪）；
  - ③ `router_decision_log.jsonl` 接 `rotate_if_oversized_with`（现在是纯 append，`decision_log.rs:91-93`）。
  - ⚠️ **原文的「顺手改成写时检查」未采纳（2026-10-30 决策记录）**：侧车的 stdout/stderr 是
    `cmd.stdout(Stdio::from(out_file))` 在 spawn 时把**文件句柄直接交给子进程**
    （`core/src/pyengine/sidecar.rs:1670-1671`），父进程根本不在写路径上 ⇒ 没有「写时」可挂钩；
    而 Windows 上重命名被子进程持有句柄的文件是共享冲突，即便改名成功子进程仍往改名后的对象继续写
    —— 「轮转」会退化成一个再不切、且原名永远空着的文件。
    现状保留 spawn 时刻轮转（`rotation::open_rotating` = 切代 + 追加 + 目录封顶）。
    **诚实残余**：单次超长运行的侧车日志可越过 `MAX_LOG_BYTES`（10 MiB）直到下次 spawn 才被切；
    不谎称已封顶，改由 W7 的 `io.sidecar_logs` 行使增长可见。

- [ ] **W6｜审计归档出口（W-E 的正确解法）**：新增「导出 → 移出活动库 → 目录按预算保留冷文件」路径；**保留**禁 UPDATE/DELETE 触发器。这是产品决策不是纯技术，先按 §8 的默认判断落。
- [ ] **W7｜写入量自观测（把「省了多少」变成可见数字，而不是口头承诺）**
  - `system.health` 附加 `io` 段：各库 `journal_mode`、`context/` 目录字节数、`plans.json` 字节数、decision log 字节数、spool 用量（`files/bytes`）。
  - 前端「诊断/存储」面板展示，并提供只读「本次会话写入次数」计数。
